# 参考吸收建议 · 知识图谱（knowledge）

> 分析对象：[JudgePeach/math-question-bank](https://github.com/JudgePeach/math-question-bank)（MathBank）· [DreZeo/examcraft-ai](https://github.com/DreZeo/examcraft-ai)（智卷工坊）
> 关联度：MathBank ★★☆（教材大纲体系与跨版本映射）· 智卷工坊 ☆（无知识点体系，仅学科/学段标签）
> 日期：2026-09-30 · 基于两仓库 README 与目录结构分析

## 1. 项目速览（与本模块相关的部分）

MathBank 内置**四套教材大纲**（人教 A 版 / 人教 B 版 / 苏教版 / 沪教版，`mathbank/resources/curriculums/` 下的共享 JSON），核心能力：

```
- 大纲作为版本化资源文件随代码管理（curriculums.py 加载 + 默认元数据）
- 切换教材版本时，题目自动智能映射到新大纲，无需重新整理
- 维度配置（章节/难度等）外置在 data_backup，可自定义
```

智卷工坊没有知识图谱概念（题目只有学科/年级元数据），本模块无直接可吸收内容。

## 2. 值得吸收的点

### 2.1 大纲即版本化 JSON 资源 ★采纳（平台标准层的实施形态）

我们"图谱冷启动流水线"（§4.4：LLM 草稿 → 人工审核 → 发布）的产物形态可以参考 MathBank：

- 标准层图谱的**源头是资源文件**（`curriculums/pep7a.json` 一类），随代码版本管理、可 diff、可回滚；
- 数据库里的 platform 层 = 资源文件的发布态（加载脚本幂等导入）；
- 好处：图谱变更走代码评审（改动可追溯），而不是直接在生产库改行——这正好补上我们设计中"平台层谁维护、怎么变更"的空白。
- 我们比它多的部分照旧：前置边（DAG）、能力点层、learning_objective 都在同一资源文件里表达。

### 2.2 跨教材映射——把我们 P2 演进预留具体化 ★重点采纳

MathBank 切换四套大纲而题目不用重标，靠的是大纲间的**映射层**。这对我们 P2 的"跨教材知识点对齐"是最直接的参考。具体化为一句话设计：

```
新增 canonical_concept（通用知识锚点）：
  人教版 kp「移项」──映射──▶ 锚点 equation.linear.transposition ◀──映射── 苏教版 kp「…」
换教材 = 换一套 platform 层节点 + 保留锚点映射；mastery_state 挂在锚点上即可跨版本延续
```

这直接解决一个我们没想清楚的问题：**学生换教材版本/转学时画像如何携带**（挂 semantic_code 会断，挂锚点则通）。P2 启动时按此设计，P1 只需保证 semantic_code 规范严格执行（已在 §3）。

### 2.3 维度配置外置 ★印证

MathBank 把章节大纲、难度维度做成 `data_backup/` 下的自定义配置。与我们的 `school.settings`（租户参数）+ platform 层资源文件三分格局互相印证：**结构（平台） / 组织覆写（学校） / 展示参数（租户设置）**各归其位，不混在一张表里。

## 3. 明确不吸收的点

| 项 | 理由 |
| --- | --- |
| 大纲只有目录树、无 prerequisite DAG | MathBank 的大纲是分类标签体系，不是知识依赖图。我们的前置链是断点诊断、前置诊断练习的根基（需求 3.3），**不能退化为纯目录树** |
| 大纲切换"全自动"映射 | 我们的场景画像挂在知识点上，映射错了会污染掌握度。跨版本映射必须 LLM 草稿 + 教研确认，不接受全自动 |
| SQLite 单机存大纲 | 同架构前提差异，略 |
